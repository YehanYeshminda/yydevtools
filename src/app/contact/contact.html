Contact YYDevTools

Have a question, spotted a bug, or want to suggest a tool? There are no accounts and no support tickets here — just email, and the code is public. Here is how to reach the person who builds and runs this site.

Email

For anything at all — questions about a tool, a privacy request, a partnership, or feedback — write to yeshanyesh12@gmail.com. Emails are read personally and usually answered within a few days.

Report a bug or request a tool

YYDevTools is open source. The fastest way to report a bug or ask for a new tool is to open an issue on GitHub, where you can see what is already planned and add your own idea:

Open an issue on GitHub · browse the source code.

Privacy and data requests

The site has no accounts and does not build a profile of you, so there is normally no personal data to export or delete. If you still have a privacy question, email the address above or read the full Privacy Policy.

What to expect

This is an independent project maintained by one developer, not a company with a support desk. Please be patient and include as much detail as you can — the tool you were using, your browser, and what you expected to happen. That context is what makes a report actually fixable.

Who runs this site

YYDevTools is built and maintained by Yehan Yeshminda, a software developer. It started as a set of utilities I kept needing and kept not trusting the existing versions of — the sort of thing where you want to decode a token or strip the location data out of a photo, search for a tool, and then think better of pasting the contents into a stranger's server.

That reservation is the whole design brief. Nearly every tool here runs entirely inside your browser, which is a verifiable claim rather than a promise: load a page, disconnect from the internet, and the tool still works. Three PDF operations genuinely cannot run in a browser and are sent to a self-hosted service instead; those are the only ones, they are labelled as hosted wherever they appear, and the Privacy Policy names them individually rather than hiding behind a general disclaimer.

The whole thing is open source, so none of this has to be taken on trust — the code that runs in your browser is the code in the repository, and you are welcome to read it.

How to write a report I can act on

Most bug reports that go nowhere fail for the same reason: the problem cannot be reproduced. Because these tools run on your device, in your browser, with your file, a description like "the PDF tool is broken" gives nothing to work from — the same tool is working for someone else on the next machine.

What helps, roughly in order of usefulness: which tool and what you were trying to do; what happened instead, including the exact wording of any error; your browser and version; and the kind of file involved — its format, rough size, and where it came from, since a PDF from a scanner behaves very differently from one exported by a word processor.

Please do not send the file itself unless you are certain it holds nothing private. A description of the file is almost always enough, and if it genuinely is not, I would rather ask you for a redacted example than receive somebody's contract or medical record by email.

Reporting a security issue

If you have found a security problem — a way to make a tool leak data off the device, a flaw in how the sandboxed HTML preview is isolated, or anything affecting the hosted PDF services — please email it rather than opening a public issue, so it can be fixed before it is advertised. Include the steps to reproduce it and what you were able to achieve. Reports are taken seriously and answered, and credit is given to anyone who wants it.
